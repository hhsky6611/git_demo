# 两人场景对话学习任务阶段

本文件把《设计思路.md》拆成可以逐个复现、逐个验收的小任务。默认一次只完成一个任务；完成并确认结果后，再进入下一个任务。每个任务都应保留必要的运行输出、请求结构或实验记录，便于回看上下文是如何变化的。

## 使用规则

1. 按编号顺序推进，不跨阶段实现后续功能。
2. 每个任务开始前，先确认输入、预期输出和验收条件。
3. 任务完成后，更新《任务进度.md》的状态、完成日期和结果摘要。
4. 复现中遇到的问题，只有在用户明确要求“写入问题”时，才写入《问题存储.md》；普通讨论不自动追加。
5. 任务失败也要记录原因和下一步，不把“代码能运行”直接当成阶段完成。
6. 项目 Markdown 文档统一存放在 `eqq/Docmd/`，后续进度和问题记录均在此目录更新。

## 阶段 0：项目准备与安全边界

### 任务 0.1：确认环境配置

目标：确认 Python、包管理器、Redis 客户端工具是否可用，并确认 `.env` 已被 `.gitignore` 忽略。

操作：

- 检查 Python 版本和虚拟环境方案。
- 检查是否可以导入后续需要的 HTTP/Anthropic 客户端。
- 检查 Redis 服务或 Docker 是否可用；使用 eqq 独立 Docker 开发环境，临时启动验证后停止服务。
- 只查看环境变量名称，不打印 token 值。

验收：记录可用的 Python 版本、依赖安装方式和 Redis 启动方式；确认密钥不会被提交或打印。

环境复现步骤见《环境复现.md》，配置文件为 `Dockerfile`、`compose.yaml` 和 `requirements.txt`。本任务只进行环境连接检查，不实现会话业务。

### 任务 0.2：建立最小项目骨架

目标：在 `eqq/` 下建立后续代码的最小结构，但不实现对话逻辑。

建议结构：

```text
eqq/
  app/
  tests/
  Docmd/
    README.md
  requirements.txt
```

验收：项目可以创建并运行一个占位命令；现有三个学习文档不被覆盖。

## 阶段 A：单次 API 调用

### 任务 A.1：读取配置并构造请求

目标：从 `.env` 读取接口配置，依据仓库根目录 `qianwneuse.md` 的调用示例构造最小请求。本阶段已通过真实请求确认当前 `/v1/messages` 接受文档中的 Messages 格式，使用 httpx 直接发送 HTTP，不依赖 SDK 转换。

请求至少包含模型名、`max_tokens`、关闭 thinking 的设置和一条 user 消息。不得把 token 写入源码。

验收：可以打印脱敏后的请求概要；请求 URL、模型名和参数来源清楚。

### 任务 A.2：发送请求并解析文本

目标：完成一次真实调用，正确处理 `content` 块数组。

验收：输出文本回答、响应模型名、`stop_reason` 和 usage；只提取 `type=text` 块；网络错误、非 2xx、缺少文本块和 `max_tokens` 截断有明确提示。

### 任务 A.3：建立 API 调用测试

目标：用 mock 响应测试文本块解析、错误响应和模型名检查。

验收：普通测试不调用真实接口；能覆盖 thinking 块、text 块和异常响应。

## 阶段 B：无 Redis 的两人物对话

### 任务 B.1：定义场景与人物配置

目标：定义一个固定场景、人物 A、人物 B 和轮流发言规则。

验收：配置中明确场景事实、人物目标、表达风格、已知信息和本轮发言限制；配置可重复使用。

#### B.1 补充示例：手动传递历史的四次对话

以下台词来自用户实际运行命令后提供的 `text` 输出。场景是河边夕阳下的小情侣相互表白，顺序为林舟 → 许晚 → 林舟 → 许晚。这是四次独立 API 请求，由用户手动将此前台词复制进下一次提示词；程序尚未自动保存历史、读取 `scenario.py` 或使用 Redis 会话缓存。配置中的 6 次发言上限尚未接入执行，本次只手动尝试了 4 次。

**第 1 次：林舟主动表白（没有历史台词）**

> 其实每次和你并肩站在这里，听着晚风，我心里都会觉得特别踏实。许晚，我很喜欢你，想以后一直这样牵着你的手走下去。

**第 2 次：许晚回应（输入中附上第 1 次台词）**

> 我也觉得此刻的风很温柔，就像你掌心的温度一样让人安心。
>
> 其实我一直都很喜欢你，林舟，往后的日子换我紧紧牵着你的手，我们一起慢慢走下去。

**第 3 次：林舟继续回应（输入中附上前 2 次台词）**

> 那我们就拉钩，谁也不许松开手。
>
> 有你在身边，连这初秋的晚风都变得格外甜了。

**第 4 次：许晚继续回应（输入中附上前 3 次台词）**

> 小拇指勾上了，可就不许再赖皮说风太甜想偷偷换口味啦。其实只要是你牵着的温度，哪怕是初秋的凉意我也觉得刚刚好。

以第 4 次为例，在 `eqq/` 目录执行下面命令可以复现相同输入。模型输出可能有所不同，不要求逐字一致。

```bash
# 如容器尚未启动，先启动开发环境。
docker compose up -d --wait

# 一次独立请求：身份 + 场景 + 已发生的台词 + 本轮回应要求。
docker compose exec dev python -m app "你扮演许晚，女，23岁，温柔坦率，偶尔俏皮，重视真诚。林舟是你的男朋友，24岁，你们刚确定恋爱关系。现在是初秋傍晚，你们站在河边观景栏杆旁，夕阳映在河面上，晚风轻轻吹过。

已经发生的对话：
林舟：其实每次和你并肩站在这里，听着晚风，我心里都会觉得特别踏实。许晚，我很喜欢你，想以后一直这样牵着你的手走下去。
许晚：我也觉得此刻的风很温柔，就像你掌心的温度一样让人安心。其实我一直都很喜欢你，林舟，往后的日子换我紧紧牵着你的手，我们一起慢慢走下去。
林舟：那我们就拉钩，谁也不许松开手。有你在身边，连这初秋的晚风都变得格外甜了。

现在请许晚回应林舟刚提出的拉钩约定，可以轻轻打趣，并自然表达自己的心意，避免重复先前的表白。只输出许晚的台词，1到3句，使用自然柔和的中文，不输出旁白，不替林舟回答，不虚构新的共同经历。"
```

**学习重点：**这四次请求的 API `messages` 都只有一条 `user` 消息。人物身份、场景和历史台词被一起放在该消息的 `content` 中；并没有因为台词写着“林舟”“许晚”就自动变成不同 API role。许晚能够接着回应，是因为本次请求明确带上了前文，而不是模型替应用记住了上次请求。

**观察与边界：**角色回应能衔接“牵手”“拉钩”，但第一句“每次和你并肩站在这里”也暗示了配置未明确给出的多次共同经历；“小拇指勾上了”则把拉钩提议推进为已发生动作。后续 B.4 可检查这类新增事实是否符合场景要求。本例未提供响应模型、usage 或完整运行日志，因此这里只记录用户提供的正文，不推断 token 消耗或服务端缓存是否命中，也不将 B.2–B.4 标记为完成。

### 任务 B.2：实现内存消息列表

目标：在内存中保存规范化消息，区分 `speaker_id` 与 API 的 `role`。

验收：每条消息有会话 ID、人物、轮次、正文和时间；历史顺序稳定；重启后丢失数据属于预期行为。

### 任务 B.3：实现单模型双角色轮流编排

目标：使用同一个模型，按 A → B → A 的顺序生成对话。

验收：编排器决定下一位发言人；每次请求都带场景、当前人物设定和必要历史；能够查看脱敏后的上下文结构。

### 任务 B.4：验证连续多轮一致性

目标：用固定问题验证人物身份、场景事实、轮次和近期事件是否保持。

验收：完成一段可重复的多轮实验，并记录实际请求消息数量、usage 和明显的角色/事实偏差。

## 阶段 C：Redis 会话存储

### 任务 C.1：启动并验证本地 Redis

目标：建立本地 Redis 连接，完成 ping、读写和删除验证。

验收：记录连接方式；Redis 不可用时程序能明确报错，不伪装为写入成功。

### 任务 C.2：设计会话 key 和数据结构

目标：分开保存会话元数据、消息和摘要。

建议 key：

```text
eqq:session:{session_id}:meta
eqq:session:{session_id}:messages
eqq:session:{session_id}:summary
```

验收：能解释每个 key 的用途、序列化格式、TTL 和最大长度策略。

### 任务 C.3：替换内存存储

目标：让两人物对话从 Redis 读取和写入会话消息。

验收：程序重启后可恢复同一会话；消息顺序正确；删除会话后不能继续恢复旧数据。

### 任务 C.4：加入 TTL 和幂等保护

目标：为会话设置过期时间，并防止同一请求重复写入消息。

验收：能验证 TTL、过期和重复请求行为；重复提交不会产生重复轮次。

## 阶段 D：上下文预算与压缩

### 任务 D.1：实现 token/长度估算

目标：为消息和上下文记录估算值，并使用真实 usage 进行对照。

验收：能看到估算值与 API `input_tokens` 的差异；明确估算不是精确 token 计数。

### 任务 D.2：实现确定性历史窗口

目标：达到阈值时保留场景、人物设定和最近 N 条消息，裁剪较早原始消息。

验收：请求不会无限增长；调试信息显示保留和丢弃的消息 ID，以及触发原因。

### 任务 D.3：实现结构化摘要

目标：将较早对话压缩为结构化摘要，同时保留原始消息。

摘要至少包含人物目标与关系变化、已确认事实、未解决问题、承诺/约束和时间线。

验收：摘要有版本、覆盖范围和生成时间；原始消息可用于检查或重新压缩；摘要明确标记为摘要。

### 任务 D.4：比较三种上下文策略

目标：使用同一组长对话，比较完整历史、窗口裁剪和摘要压缩。

验收：记录事实回忆、角色一致性、输入 token、延迟和明显错误，形成一份实验结论。

## 阶段 E：缓存与双模型扩展

### 任务 E.1：区分会话状态和结果缓存

目标：明确 Redis 会话数据、应用生成结果缓存和服务端 Prompt Cache 的边界。

验收：缓存键包含模型、system、消息、参数和版本；不缓存依赖实时状态或随机性高的请求；能查看命中/未命中原因。

### 任务 E.2：实现可控的结果缓存实验

目标：只对完全相同且允许复用的请求进行缓存，并比较延迟与一致性。

验收：修改任一关键输入会失效；缓存过期和清理可验证；不会把缓存命中误报为服务端 prompt cache 命中。

### 任务 E.3：增加双模型角色开关

目标：让 A、B 可配置不同模型，保留单模型双角色作为对照组。

验收：日志能区分每一轮使用的模型、人物、上下文和调用链；能够比较连贯性、延迟、token 和成本。

### 任务 E.4：完成学习项目总结

目标：整理从 API、Redis、上下文窗口、摘要到缓存的实验记录。

验收：能够用实际日志解释上下文如何构造、何时压缩、Redis 保存什么，以及不同策略的取舍；再决定是否增加网页界面或向量检索。
