# 两人场景对话与上下文管理：学习项目设计思路

## 1. 项目目标

通过一个可运行、可观察的小型对话应用，逐步理解模型 API 的无状态调用方式，以及应用如何组织上下文、保存对话、压缩历史和管理缓存。

用户可以设定一个场景和两个人物，启动一段有来有回的对话；每次调用模型时，系统根据当前人物、场景、对话历史和轮次生成请求。Redis 保存可恢复的会话状态，并提供清理和过期机制。页面或命令行应能检查实际发送给模型的上下文，比较压缩前后的内容与 token 估算值。

学习重点不是做一个复杂 Agent，而是把以下关系看清楚：

- 模型 API 通常不替应用保存完整会话；应用要自行提交本轮需要的历史。
- 人物设定、场景、对话消息、摘要和运行状态是不同类型的上下文，生命周期也不同。
- Redis 是应用侧的状态存储/缓存；它不等于模型厂商的 Prompt Cache。
- 上下文压缩是有损的信息取舍，需要可检查、可比较、可回退。
- “两个人物对话”是编排模式；使用一个模型扮演两个角色，不等于两个模型在互相通信。

## 2. 对整体思路的评估

这是一个适合边做边学的项目，范围可控，又覆盖 API 调用、会话状态、缓存、历史裁剪与压缩。现有 `.env.example` 指向 Anthropic Messages 格式的 Qwen 中转配置，已有说明还验证了 `system`、多轮 `messages`、流式响应和响应内容块结构，可以作为第一阶段的接口依据。实际调用时要从 `content` 中提取 `type=text` 的内容，并检查返回的 `model`；中转对未知模型名可能静默回落，因此不能仅凭 HTTP 200 认定使用了预期模型。

需要控制两个容易混淆的变量：

1. 先用一个模型依次生成角色 A 和角色 B 的发言，记录每次请求。第一版若同时让两个模型互相调用，排查问题时就很难分清是提示词、编排、模型差异还是上下文拼接造成的。
2. 先实现完整历史，再实现摘要压缩。对话很短时压缩没有收益；需要通过可重复的长对话观察上下文长度、摘要质量和调用成本的变化。

Redis 本身不会自动让模型“记住”对话。它负责保存应用构造下一次请求所需的数据；每次请求仍由应用从 Redis 读取、整理并提交给 API。初期可用本机 Redis 或 Docker Redis，Redis 不可用时明确报错或进入只读演示模式，不应静默丢失会话。

## 3. 推荐的最小产品形态

建议先做本地命令行交互，稳定后再增加一个简单网页。命令行更容易聚焦于请求体、Redis 数据和上下文变化；后续网页只作为可视化与操作入口，不改变核心会话服务。

一次会话配置至少包含：

- 场景描述：时间、地点、当前事件、氛围，以及本场景不可违反的事实。
- 人物 A / B：名称、目标、性格、已知信息、表达风格；避免把提示词写成无限扩张的背景资料。
- 对话规则：轮流发言、单次发言长度、是否允许旁白、结束条件。
- 会话设置：模型、输出上限、历史窗口策略、TTL、压缩阈值。

一条消息建议采用稳定结构：`message_id`、`session_id`、`speaker_id`、`role`、`content`、`turn_index`、`created_at`、`token_estimate`。其中 `speaker_id` 表示 A/B 人物，API 的 `role` 表示 `user`/`assistant`，两者不要混为一谈。可以把当前发言人物及场景规则放在 `system` 中，把规范化后的过往对话映射为 `messages`；要先验证连续的 assistant/user 消息是否符合当前中转服务的实际接受规则，必要时将人物说话内容统一包在 user 轮输入中，避免依赖未验证的 role 序列行为。

## 4. 逻辑架构与数据流

```text
CLI / Web
   │ 创建会话、继续对话、查看上下文、清空会话
   ▼
Conversation Service
   ├── Session Store（Redis：会话元数据、消息、摘要、TTL）
   ├── Context Builder（场景 + 人物 + 摘要 + 历史窗口 + 当前任务）
   ├── Token Estimator（预算估算与阈值判断）
   ├── Compactor（按规则生成摘要、保留近期消息）
   └── Model Client（Anthropic Messages API 兼容接口）
              │
              ▼
         Qwen 中转接口
```

一轮对话的顺序：读取会话 → 确定下一位发言角色 → 组装上下文 → 检查预算 → 必要时压缩 → 调用模型 → 解析文本块与 usage → 写入新消息/元数据 → 返回结果和调试信息。每个阶段都应可单独观察，避免把 API、Redis 与压缩逻辑塞在同一个函数里。

## 5. 分阶段学习路径

### 阶段 A：单次 API 调用

用现有环境配置发出一次请求，验证认证头、模型名、`thinking` 设置、`max_tokens`、超时与错误处理。解析 `content` 数组中的文本块，记录响应模型名、stop reason 和 usage。密钥只从环境变量读取，日志不得输出密钥、完整鉴权头或敏感会话文本。

验收：能够从命令行发起请求、看到回答和 usage；将网络失败、非 2xx、缺少文本块、`max_tokens` 截断区分处理。

### 阶段 B：无 Redis 的两人物对话

内存中保存消息列表。场景固定为一个可复现实例，A、B 轮流发言；每一轮只调用同一个模型，提示中明确“本轮扮演谁、对方是谁、已发生什么”。每次请求都打印脱敏后的上下文结构和消息数量。

验收：人物轮换正确，场景事实可在后续轮次保持，历史顺序正确；重启后丢失会话是预期现象。

### 阶段 C：Redis 会话存储

把会话元数据、消息、摘要分开保存，设置明确 TTL，并提供查看、删除、过期刷新命令。先采用简单、可读的数据结构；消息写入需考虑重复提交与并发轮次，至少用 `turn_index` 或请求幂等 ID 防止重复落库。Redis key 带项目命名空间，例如 `eqq:session:{session_id}:meta`、`...:messages`、`...:summary`。设定合理最大会话条数/体积，避免只依赖 TTL。

验收：同一会话重启后可恢复；过期/删除按预期生效；Redis 断开时给出明确错误且不伪装为写入成功。

### 阶段 D：上下文预算与压缩

先实现“保留场景与人物设定 + 保留最近 N 条消息”的确定性窗口策略，再加模型摘要。达到阈值时，把较早消息压成结构化摘要，至少保留：人物目标与关系变化、已确认事实、未解决问题、承诺/约束、时间线；近期原始消息继续保留。每次压缩保存摘要版本、覆盖的消息范围、生成时间和 token 估算，调试视图能并排显示压缩前后内容。

不要把摘要作为唯一事实源：保留原始消息用于检查和重新压缩；对重要约束和场景事实保留独立字段。第一版以保留关键事实和近期连贯性为目标，而不是追求某个摘要模型自动处理所有知识。

验收：长对话能把请求控制在预算内；摘要不会悄悄覆盖场景设定；用户可以查看和重置摘要；有一组固定长对话用例检查事实、人物目标和最近事件的保留情况。

### 阶段 E：缓存与双模型扩展

先把缓存概念拆开学习：Redis 中的会话数据是应用状态；可选的生成结果缓存是应用缓存；服务端 prompt caching 是否生效由接口/模型提供方决定，不能从 Redis 命中推断。只有对完全相同、允许复用的请求才考虑结果缓存，并把模型、system、消息、参数版本纳入缓存键；带随机性或依赖实时状态的输出默认不缓存。

最后再增加“两个模型各自扮演一个人物”的实验开关。记录 A→B→A 的调用链、各自模型、system 与历史输入，比较同一模型双角色和双模型角色在连贯性、延迟、token、成本上的差异。不要将两套编排同时作为默认路径。

## 6. 上下文组装建议

每次调用的上下文层次保持稳定，方便比较：

1. 场景规则和不可变事实。
2. 本轮发言角色的人物卡与行为边界。
3. 历史摘要（若存在，显式标明为摘要而非逐字记录）。
4. 最近若干条原始对话。
5. 当前轮次任务：以指定角色回应，遵守场景和轮流规则。

在调试输出中记录各部分字符数/token 估算、被保留或丢弃的消息 ID、压缩触发原因、模型响应 usage。先用模型返回的 `usage.input_tokens` 校准本地估算，不要把字符数当成精确 token 数。为模型输入设置软阈值并留出输出预算；中转的最大上下文能力如未确认，应作为配置而不是写死的事实。

## 7. 技术选型建议

- 语言：建议 Python，便于快速学习请求构造、Redis 数据模型和 CLI；若目标是练习已有技术栈，可替换语言而不改变分层。
- 模型客户端：沿用 Anthropic Messages API 兼容格式。可以使用已验证的 `anthropic` SDK，或用标准 HTTP 客户端直接调用；第一版只保留一种实现，减少鉴权头差异。
- Redis：本地 Redis，开发阶段可通过 Docker Compose 启动；会话写入应明确 TTL 和最大长度。
- 配置：现有 `.env.example` 已列出 `QWEN_BASE_URL`、`QWEN_ENDPOINT`、`QWEN_MODEL`、`QWEN_AUTH_TOKEN`、Anthropic 版本和输出上限。后续实现再补 Redis URL/host、端口、DB、TTL、上下文预算等变量；真实 `.env` 不进入文档、日志或版本控制。
- 测试：API 客户端、上下文构造、压缩策略和 Redis 存储分别测试；用 mock 模型测试业务流程，避免普通测试消耗真实 API 额度。

初始设计时仓库尚无应用框架、依赖清单或 Redis 配置；任务 0.1 已建立 `eqq/` 下的 Docker 开发环境，任务 0.2 建立 `app/`、`tests/` 和 `Docmd/README.md`。项目 Markdown 文档统一位于 `eqq/Docmd/`，Docker 配置为 `compose.yaml`；后续按阶段逐步实现 CLI 和业务服务。

## 8. 必须记录的可观察指标

- 会话 ID、轮次、发言人物、响应模型名、stop reason。
- 请求消息数、输入/输出 token usage、预算估算、压缩前后估算。
- Redis 读取/写入/过期状态、结果缓存是否命中（若实现）。
- 每次压缩覆盖的消息范围、摘要版本与摘要内容。
- API 延迟与错误类别；不记录认证信息，默认限制原始对话日志并允许关闭正文记录。

观察指标的用途是解释行为和成本；不要把 Redis 命中率当成模型 prompt cache 命中率，也不要把 API 返回的缓存 token 字段假定为一定受中转支持。

## 9. 风险与边界

- 模型可能不按角色轮换或场景规则行事；编排器必须决定下一位发言人，不能完全交给模型。
- 摘要可能遗漏、篡改或混淆事实；保存原始记录，摘要可重建，并设计固定回归场景。
- Redis 若只存一份不断增长的 JSON，会带来读写竞争和大值问题；按会话元数据、消息和摘要分开管理，并控制长度。
- 重试可能重复生成或重复写消息；区分请求幂等、模型调用与存储提交，写入前检查请求 ID。
- 会话内容可能包含个人信息；本地学习项目也要提供清空方式，设短 TTL，避免将正文送入不必要的日志。
- 接口中转的模型路由与 token 统计可能存在差异；读取响应模型和 usage，并在文档中记录实测结果。

## 10. 建议的学习成果

完成前四阶段后，应能回答并通过实际日志证明：一次对话请求由哪些上下文组成；消息如何在 Redis 中恢复；角色身份如何映射到 API role；何时触发裁剪或摘要；摘要如何影响后续回答；Redis 缓存与服务端 prompt caching 有何区别；长上下文对 token、延迟和连贯性产生什么变化。

建议最后产出一份短实验记录，使用同一组场景与问题分别测试完整历史、窗口裁剪、摘要压缩三种策略，比较事实回忆、角色一致性、输入 token 和延迟。这样能把“学习了功能”转成可验证的结论，再决定是否需要网页界面、向量检索或双模型编排。
